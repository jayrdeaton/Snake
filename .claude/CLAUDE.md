# Snake

A classic Snake game with Solo, Vs CPU, and local 2-player pass-and-play modes (Expo/React Native, Skia-rendered). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem — depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/resizable-input`, `@rific/scroll-view`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/achievements`, `@tastic/core`, `@tastic/hud`, `@tastic/input`, `@tastic/profile`, `@tastic/split-screen`. (`@rific/drawer` was a dependency until 2026-09-17 — removed along with the dead `HistoryDrawerContainer` code that was its only call site, see below.) The most complex app in the fleet to migrate so far after CashierFu-Utility — real Redux Toolkit state (`@reduxjs/toolkit`, `react-redux`, `redux-persist`), plus dependencies no other game in the fleet has yet (`react-native-keyboard-controller`, `expo-linking`, `expo-secure-store`, `@shopify/flash-list`).

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (17 suites, 215 tests)
npm run test:watch     # Jest --watchAll
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) — `verify` doesn't include a build step.

There are no per-profile `build:development`/`build:preview`/`build:production` or `update:development`/`update:preview`/`update:production` scripts in this app's `package.json` at all, and no `npm run verify && ` prefix anywhere in it — just one bare `"build": "rific-updater-build"` and `"update": "rific-updater-update"`, delegating straight to `@rific/updater`'s own CLI bins, which run this app's `npm run verify` as their first step internally, before any build/update logic proceeds. See [`@rific/updater`'s own README](../Expo-Updater/README.md) ("Build & update scripts" / "Verify-gating lives in the CLI, not in `package.json`") for the full mechanism — the per-script `npm run verify && ` prefix this paragraph used to describe (and which every sibling app's CLAUDE.md still describes the same way) predates these bins and no longer applies once an app is on them.

**2026-09-17 — a live browser check of AirHockey's `/loadout` screen (its migration this same round is byte-for-byte the same shape as this app's own) turned up a real bug in `@rific/core`, upstream of this app's own `Theme.tsx`/`Providers.tsx`.** `createSettingsContext`'s `set()` called the consumer's `onChange` *inside* the `useState` updater passed to `setSettings` — a `useState` updater must be pure, since React can invoke it outside the originating `set()` call (e.g. replaying a queued update while resolving a later render of the very same Provider), and when that happened, `onChange` (which `Theme.tsx` wires straight to `dispatch(themeActions.initialize(...))`) fired synchronously mid-render of an unrelated component — a genuine "Cannot update a component while rendering a different component" React warning. ## Fleet-wide drift audit round 2 (2026-09-18)

A second, more comprehensive fleet-wide scan (same 5 apps) found seven real gaps here, all fixed:

- **`_layout.tsx` never set the root window's background color, unlike every sibling app** — a real corner-flash risk during a push transition on Android/web, where the OS-level window background (not any React-rendered view) briefly shows through before content paints. ## Fleet package extraction round 2 (2026-09-18)

A second round of duplicated-code extractions across this app and 4 siblings (AirHockey, BoxHockey, Pong, LightCycles) — 7 of 8 candidates examined actually apply to this app (the 8th, a SplashGate-wrapper pattern, doesn't — see below). This app is now on `@rific/core@0.1.4`, `@tastic/achievements@0.1.2`, `@tastic/hud@0.11.0`, `@tastic/profile@0.6.0`, `@tastic/core@0.7.0`, and `@rific/auto-paper@0.11.1` (all yalc-linked, same rollout convention as the 2026-09-17 extraction round above):

- **`src/utils/navigation.ts`'s `safeBack` now binds to `@rific/core`'s shared implementation** instead of a hand-rolled local function. The file shrinks to a `configureNavigation({ router })` call — injecting expo-router's `router` object via the same `OptionalModule`/`createModuleConfig` convention `@rific/scanner`/`@rific/resizable-input` already use for their own optional native peers — plus a re-export of `safeBack`, keeping `@rific/core` free of a hard `expo-router` dependency it doesn't otherwise have. Every call site (`safeBack()`, `onBack={safeBack}`, `onHome={safeBack}`, `onConfirm={safeBack}`) needed zero changes, since the extracted function keeps its exact zero-argument signature — that constraint (not a design preference) is why it's injected via module config rather than taking `router` as a parameter.
- **`useGameStats.tsx`'s profile-id-to-seat translation and `game.tsx`'s device-wide-unlock broadcast now go through `@tastic/achievements`' new `mapUnlocksBySeat`/`broadcastDeviceUnlocks`** instead of a hand-rolled loop and ternary. `recordRoundOutcome`'s existing `seatProfileIds` local (still built the same way, since `applyRoundOutcome` separately needs the flattened id list) now feeds `mapUnlocksBySeat([1, 2] as SnakeId[], seatProfileIds, result.profiles)` directly. `game.tsx`'s gameOver effect replaces its old single-ternary broadcast expression with `mode === 'twoPlayer' ? broadcastDeviceUnlocks([1, 2] as SnakeId[], unlocked.profiles, unlocked.device) : {}`. One real, non-cosmetic shape change from this swap: `achievementUnlocks` on a round where nothing unlocked used to materialize as `{1: [], 2: []}` and now comes back as `{}` — confirmed behaviorally inert at `GameOverDialog.tsx`'s own read site (`(achievementUnlocks[seat] ?? []).map(...)` and the summed `.length` check both treat the two shapes identically), but worth knowing if a future consumer ever does `Object.keys(achievementUnlocks).length` instead of reading a specific seat.
- **`game.tsx`'s "Quit Match?" confirmation now uses `@tastic/hud`'s `useQuitConfirmation`.** Its real, current signature is `useQuitConfirmation(hasProgress: () => boolean, onConfirmedBack: () => void)` — a lazy getter, not a plain boolean. That's a correction the hook went through after its first version shipped as a plain-boolean API: that version created a genuine circular render dependency in AirHockey/BoxHockey/Pong (`confirmVisible` → the `paused` flag those apps derive from it → `useGameState()` → the live scores/lives/bricks state → `hasProgress` → `confirmVisible` again), since those three apps have to compute `paused` and hand it to their own game-state hook before that hook has returned the very state `hasProgress` needs to read. **Snake never had that circular dependency in the first place** — `useSnakeState` takes no `paused` parameter derived from `confirmVisible` at all (this app's game loop doesn't gate on the quit dialog being open), so `humanScore`/`opponentScore` are already-resolved locals by the time the hook is called. Adopting the corrected lazy-getter signature here was accordingly a trivial one-line wrap, not a workaround: `useQuitConfirmation(() => humanScore > 0 || (opponentScore ?? 0) > 0, safeBack)` (`game.tsx:223`). The returned `confirmVisible`/`requestBack`/`cancelBack` replace the old local `useState` + `useCallback` pair 1:1; `<ConfirmDialog>`'s own `onConfirm={safeBack}` is untouched, since that was always the dialog's own prop, not something the hook owns.
- **`achievements.tsx`'s catalog-row computation and its "ALL ACHIEVEMENTS"/"ACTIVITY" sections now come from `@tastic/achievements`' `getAchievementCatalogRows` and `@tastic/hud`'s `AchievementCatalogSection`/`ActivityStatSection`.** The screen's local `MS_PER_DAY`/`startOfDay`/`unlockedLabel` day-diff formatter, its `ACHIEVEMENT_CATALOG.map(...)` loop, and its `<StatSection label='ACTIVITY'>` block are all gone, replaced by `<ActivityStatSection stats={statsView} />` and `<AchievementCatalogSection rows={getAchievementCatalogRows(ACHIEVEMENT_CATALOG, stats, statsView, unlockedAchievements, effectiveProfileId)} />`. Confirmed `@tastic/hud`'s `AchievementCatalogSection` is on the corrected, real-import state, not the transient workaround: it imports `AchievementCatalogRow` as a genuine type-only peer dependency straight from `@tastic/achievements` (an earlier draft of that hud component had briefly duplicated the type locally, before `@tastic/achievements` had actually published `catalogRows.ts` — that duplication is gone). The OVERALL/VERSUS/per-mode/PLAYER RANKINGS sections, which differ per app, are untouched, as is this screen's `!loaded` guard (it already rendered a real `BaseStatsScreen` shell with a "Loading…" message rather than a bare `null`, fixed in the drift-audit round above, so this extraction had nothing to do there).
- **`profiles.tsx` is now a thin route wrapper around `@tastic/profile`'s new `ProfilesScreen` component**, replacing this app's own hand-rolled container `View`, theme-derived background/foreground colors, back `IconButton`, and `commitPendingEdit()`-then-`safeBack()` composition — all of that now lives inside `ProfilesScreen` itself. This app's `onCreate`/`onSave`/`onDelete`/`onBack` callbacks are otherwise unchanged: Snake's `CreateProfileInput` was already `@tastic/profile`'s own base `{name, color, tag}` shape (unlike BoxHockey's `controlScheme`-widened one or LightCycles' `keyScheme`-widened one), so `onCreate={(patch) => createProfile(patch)}` needed no field-composing adaptation.
- **`_layout.tsx`'s root-window-background/corner-flash fix (added just one day earlier, in the drift-audit round 2 entry above) now comes from `@tastic/core`'s new `useThemedRootBackground` hook** instead of this app's own module-level `SystemUI.setBackgroundColorAsync` call plus a local `useEffect` and inline `screenOptions` object. `RootNavigator`'s `<Stack screenOptions={useThemedRootBackground(dark, false)}>` replaces that inline object. The `gestureEnabled: false` rationale comment (iOS's native swipe-back gesture otherwise fighting `TouchInputLayer`'s own swipe-to-turn Pan gestures on `/game`) stays put as prose above the hook call, since the hook deliberately takes `gestureEnabled` as its second parameter rather than hardcoding it — that's a separate, app-specific concern from the corner-flash fix itself, and a future consumer of this hook without Snake's gesture conflict shouldn't be silently opted into disabled back-swipe. Snake's four explicit `<Stack.Screen name=.../>` children (the only one of the 5 apps with any) is exactly why this landed as a hook returning a plain options object rather than a wrapping component around `<Stack>` — a component would need its own `children` passthrough prop that only this app would ever use.
- **`splashgate-wrapper` does not apply to this app.** Snake stores its settings in Redux directly and has no `AsyncStorage`-backed settings-plus-`SplashGate` architecture for that candidate to touch, so it was correctly considered and skipped, not overlooked.
- **`Theme.tsx`'s `<AutoPaperProvider>` wiring now goes through `@rific/auto-paper`'s new `useThemeBridgeProps` hook.** The existing `useSelector(state => state.theme, shallowEqual)`, `dispatch(themeActions.initialize(...))`, and one-shot `markSplashReady('theme')` lines are all unchanged — this hook only replaces the trailing `initialValue={settings} onChange={onChange} onReady={onReady}` prop list with a single memoized `{...bridgeProps}` spread. Snake's two extra `<AutoPaperProvider>` props (`expoBlur={ExpoBlur}` and `fontFamily={DISPLAY_FONT_FAMILY}`, fed by this file's own dynamic `useFonts()` load and separate `'fonts'` splash-gate entry) stay appended after the spread exactly as before — the hook is deliberately just a props-returning helper, not a wrapping `<Theme>` component, since a component would have had to re-expose that whole app-specific `ProviderProps` surface as passthrough for no benefit. `src/__tests__/components/Theme.test.tsx`'s `jest.mock('@rific/auto-paper', ...)` factory needed updating to also export `useThemeBridgeProps` alongside its existing `Provider`/`themeActions` mocks, or the real `Theme.tsx` call throws "useThemeBridgeProps is not a function" against the mocked module — the only one of the 5 apps with a test that actually exercises this file.

## Testing

- Framework: Jest (`@infinitetoken/jest-config/expo`, `jest-expo` preset)
- Tests live in `src/__tests__/`, mirroring the source subfolder structure (`app/`, `components/`, `constants/`, `redux/`, `utils/`)
- Native/Expo module mocks live in `src/__mocks__/`, one file per module (plus one scoped subpath), picked up automatically (no `jest.mock()` call needed) — see Tooling above
- `jest.setup.cjs` holds only genuine setup-file concerns: process-level error handlers, RAF polyfills, the `IS_REACT_ACT_ENVIRONMENT` flag

## Architecture

```
src/
  app/          - expo-router routes
  components/   - UI components (board rendering, controls, dialogs, providers)
  constants/    - static config, game params
  hooks/        - custom hooks, sounds/
  redux/        - Redux Toolkit store, slices, persistence
  types/        - shared TypeScript types
  utils/        - grid/engine logic, AI, splash gate, validation
  __tests__/    - test suites
  __mocks__/    - manual Jest mocks for native/Expo modules
```
